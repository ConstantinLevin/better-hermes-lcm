## A. Per-file verdicts

**The three most important results are:**

- **Raw-message storage is not an exact archive.** It drops message fields outside its fixed column set and cannot distinguish structured content from a string containing the same JSON. This affects ordinary ingestion, without enabling a lossy option. **ST1**
- **Reconciliation can discard new occurrences and attach incorrect provenance.** Probes skipped a repeated exchange with newer timestamps, mapped explicit store ID 3 to identical content at ID 1, and discarded the surrounding text of a quoted externalized reference when computing identity. **RC1, RC2, RC4**
- **A supported legacy DAG layout is decoded incorrectly after migration.** The probe returned the old recovery hint as `earliest_at` and returned an empty `expand_hint`. The data remains in SQLite, but normal DAG reads misinterpret it. **DG1**

There are **40 findings**, including conditional and low-impact defects—not just the most serious ones.

Configuration terminology below distinguishes an enabled code path from an observed production incident. “Default” means no opt-in feature is required; the stated data or failure condition must still occur. The documented configuration disables externalization, active stubbing, transcript GC and sensitive redaction by default, and leaves ignore patterns empty. The deployment design also leaves deferred maintenance off. Sources: [README.md:479](README.md:479), [docs/fork-design.md:388](docs/fork-design.md:388). I did not inspect private runtime configuration or the live database.

### store.py

Responsible for storing and retrieving messages, maintaining message FTS, recording metadata, and exposing mutation, GC and backup operations.

**ST1 — The stored representation loses message fields and original content type.**

The insert paths retain selected fields only; there is no complete original-message envelope. Fields such as `name`, `reasoning_content` and native replay metadata disappear. Structured `content` is serialized into the same TEXT representation used for an ordinary string; reconstruction returns that string without restoring its original type. See [store.py:476](store.py:476), [store.py:543](store.py:543), [store.py:1695](store.py:1695), [message_content.py:30](message_content.py:30).

**Trigger/configuration:** Default ingestion whenever those fields or structured content occur. Hermes really uses additional replay fields; this is not merely a hypothetical input shape. run_agent.py:1103 (Hermes Agent host internals; path elided)

**Consequence:** Exact recovery is impossible. Probe P28 confirmed both missing fields and a collision between a content-parts array and its JSON-string representation.

**ST2 — A short token-estimate list silently drops the message suffix.**

`_append_protected_batch` iterates `zip(messages, token_estimates)` without checking equal lengths. Two messages with one estimate produce one successful insertion and no error. [store.py:533](store.py:533)

**Trigger/configuration:** Any window, malformed caller input to the batch API. I did not find a currently normal engine call deliberately supplying unequal lengths.

**Consequence:** Raw messages disappear at the storage boundary. P01 reproduced it. A’s bulk insertion iterates every prepared input, avoiding this particular parallel-array hazard. [conversation-store.ts:954](lossless-claw v1.0.0 src/store/conversation-store.ts:954)

**ST3 — GC lacks rollback on failure and validates against an unprotected snapshot.**

GC reads role, pin state and content before its UPDATE, then calls the archive callback and commits without an exception rollback boundary. The UPDATE also does not repeat the validated pin/content conditions. [store.py:608](store.py:608)

**Trigger/configuration:** Transcript GC enabled; callback/commit failure, interruption, or a competing connection modifying or pinning the row. GC is disabled in the documented default configuration.

**Consequence:** A failed operation can leave rewritten content pending, later committed by an unrelated operation; a concurrent pin/content change can be overwritten. P02 raised inside the callback: the placeholder remained in an open transaction and a subsequent append committed it. The engine’s callback introduces an additional swallowed-error problem noted in part D.

**ST4 — The public flush can commit another thread’s incomplete batch.**

`commit()` does not acquire `_write_lock`; `backup()` likewise has no ownership boundary. Maintenance calls the public flush before copying the database. [store.py:1722](store.py:1722), [maintenance.py:56](maintenance.py:56)

**Trigger/configuration:** Default storage with a backup/flush overlapping ingestion on the same store instance.

**Consequence:** Batch rollback ceases to be atomic. P30 paused between two batch rows, called `commit()` from another thread, then failed the batch: the first row survived. A failed batch can therefore leave a durable partial ingest and ambiguous replay state.

**ST5 — Several recovery queries exceed SQLite’s parameter limit instead of batching.**

`get_batch` and `get_time_bounds` construct one placeholder per supplied ID. DAG child retrieval and source-time aggregation do the same. [store.py:659](store.py:659), [store.py:1057](store.py:1057), [dag.py:757](dag.py:757), [dag.py:860](dag.py:860)

**Trigger/configuration:** Any configuration when the requested ID set exceeds the SQLite build’s variable limit. The audit interpreter reports 250,000; P06 lowered its connection limit to four and confirmed failure on five IDs.

**Consequence:** Bulk recovery or publication fails on an otherwise valid archive. This is a correctness limit, not a summarization preference to scale with the window.

**ST6 — LIKE relevance/hybrid search can discard better-ranked matches before ranking them.**

SQL uses a constant `directness_expr`, caps candidates, and only then calculates actual directness in Python. Its candidate ordering therefore differs from its final ordering. [store.py:1552](store.py:1552), [store.py:1632](store.py:1632), [store.py:249](store.py:249)

**Trigger/configuration:** Default search, LIKE fallback, relevance or hybrid sorting, enough tied coarse-score matches to exceed the candidate cap.

**Consequence:** Relevant sources become undiscoverable through the requested ranking, with no incomplete-search marker. P29 placed an older `alpha beta 🚀` answer before 501 repeated-`alpha` distractors; the better directness match was excluded.

**ST7 — Collection APIs can silently return less than their apparent/requested scope.**

`load_session_window` silently clamps both requested sides to 12. `get_session_messages`, documented as obtaining “all messages,” defaults to 10,000 and returns an ordinary list without completeness metadata. [store.py:820](store.py:820), [store.py:848](store.py:848)

**Trigger/configuration:** Direct calls requesting a larger window or treating the default session result as exhaustive. Current inspected window consumers request within the clamp; the concrete unpaged rollover consumer is PL4.

**Consequence:** The caller cannot distinguish exhaustion from an internal bound. P38 requested 20 messages on each side of an anchor in a 30-row session and received 25 without a marker.

**Checked and found sound:** The tail query limits descending IDs and then restores chronological order; `scan_evidence_rows` explicitly reports totals and truncation from one SQL snapshot. The main reconciliation and stored-placeholder-count consumers correctly paginate `get_session_messages_after`; their 10,000-row page size is **not** a history ceiling. [store.py:871](store.py:871), [store.py:673](store.py:673), [reconcile.py:966](reconcile.py:966), [placeholder_ledger.py:372](placeholder_ledger.py:372)

The unguarded raw-session deletion primitive also participates in **DG2**. [store.py:581](store.py:581)

### dag.py

Responsible for summary-node storage, source edges encoded in JSON, frontier queries, summary search, traversal, deletion and reassignment.

**DG1 — Legacy column migration and positional decoding disagree.**

Fresh tables place `earliest_at` and `latest_at` before `expand_hint`. An older table already containing `expand_hint` receives the two new columns at its end. Reads use `SELECT *`, while `_row_to_node` assumes the fresh-table order. [dag.py:187](dag.py:187), [dag.py:224](dag.py:224), [dag.py:909](dag.py:909)

**Trigger/configuration:** Upgrading an existing database with that legacy layout; no opt-in feature required.

**Consequence:** Incorrect time bounds and missing or mis-typed recovery hints throughout normal DAG reads. P07 returned `earliest_at="recover invoice"` and `expand_hint=""`. This is a decoding defect, not deletion of the underlying SQLite values. A’s corresponding reads name their projected fields explicitly. [summary-store.ts:762](lossless-claw v1.0.0 src/store/summary-store.ts:762)

**DG2 — Provenance has neither insertion validation nor deletion protection.**

`add_node` accepts empty, nonexistent, null, incorrectly typed and structurally invalid source IDs. JSON edges have no foreign-key enforcement. Node deletion does not check incoming references; raw-session deletion can likewise leave dangling leaves. [dag.py:250](dag.py:250), [dag.py:296](dag.py:296), [store.py:581](store.py:581)

The consequences are not confined to imperfect diagnostics:

- A null node-source value poisons frontier `NOT IN`, producing a zero token total. P10 reproduced this. [dag.py:425](dag.py:425)
- Missing children disappear from joins/descriptions without an explicit broken-edge record. P11 reproduced `num_sources=1` with no child. [dag.py:757](dag.py:757), [dag.py:877](dag.py:877)
- `_node_matches_source` uses `UNION ALL`; a cycle does not terminate normally. P12 required a SQLite progress-handler interruption. [dag.py:813](dag.py:813)
- Traversal casts source values to integers, potentially interpreting malformed identifiers as different identifiers. [dag.py:787](dag.py:787)

**Trigger/configuration:** Invalid publication, imported/damaged data, or deletion of referenced records. The default compaction caller can publish an empty source list because it does not require complete source mapping. Direct destructive APIs are not ordinary default compaction operations. [compaction.py:996](compaction.py:996)

**Consequence:** Missing or incorrect provenance, concealed frontier contents, or unavailable recovery.

A provides useful—but not complete—protection through relational source tables and `ON DELETE RESTRICT`, with foreign keys enabled. This comparison does **not** establish that A prevents cycles. [migration.ts:1256](lossless-claw v1.0.0 src/db/migration.ts:1256), [connection.ts:50](lossless-claw v1.0.0 src/db/connection.ts:50)

**DG3 — Node, sidecar and frontier publication have separate commit boundaries.**

`add_node` commits immediately. The caller subsequently writes node metadata, invalidates derived state, potentially runs GC, and advances the lifecycle frontier. [dag.py:272](dag.py:272), [compaction.py:1019](compaction.py:1019), [node_meta.py:84](node_meta.py:84)

**Trigger/configuration:** Default compaction; interruption or failure between those operations.

**Consequence:** A persisted node can coexist with an old frontier or missing sidecar/invalidation state. Retry can republish the same span and change the DAG. This is an existing reported residual, confirmed in current code. A’s leaf publication wraps summary insertion, source links and context replacement in one transaction. [compaction.ts:2324](lossless-claw v1.0.0 src/compaction.ts:2324)

**DG4 — DAG LIKE search limits unordered rows before applying the requested sort.**

The SQL has `LIMIT/OFFSET` without `ORDER BY`. Python sorts the fetched subset and, absent a source filter, returns immediately. [dag.py:722](dag.py:722)

**Trigger/configuration:** Default search whenever LIKE fallback is selected and matches exceed the first fetch.

**Consequence:** Both recency and relevance/hybrid results can omit better matches. P08 created 60 chronological matching nodes; a newest-first request returned node 50 instead of node 60.

**DG5 — Source filtering occurs after the global search candidate cap.**

FTS and LIKE fetch candidates without the descendant-source filter, then test lineage in Python and stop at the candidate ceiling. [dag.py:635](dag.py:635), [dag.py:657](dag.py:657), [dag.py:731](dag.py:731)

**Trigger/configuration:** Default source-filtered search, with enough higher-ranked nodes belonging to other sources.

**Consequence:** An ordinary empty result can mean “matching source was beyond our scan.” P09 returned no result despite an existing matching node beneath 600 newer wrong-source candidates.

**DG6 — Descendant resolution silently exposes only the first bounded prefix.**

`source_message_ids` orders by store ID, applies `LIMIT`, and returns no total, continuation or incomplete flag. The recall caller uses a per-node limit of **four**, before inspecting descendant message content. [dag.py:770](dag.py:770), [tools.py:315](tools.py:315), [tools.py:4398](tools.py:4398)

**Trigger/configuration:** Default summary-assisted recall for a node covering more than four messages.

**Consequence:** Relevant later sources can be absent from evidence retrieval without a statement that only the earliest descendants were searched. A node expansion hint supplies a possible recovery route, but does not disclose this omitted scope. P37 returned `[1,2,3,4]` for a five-source node with no completeness information.

**DG7 — The session-node API enables an incomplete frontier calculation.**

`get_session_nodes` is a bounded list with no continuation. The engine requests 100,000 nodes, then computes the frontier from that partial graph. Its SQL frontier-token calculation is uncapped, so the two views can disagree. [dag.py:463](dag.py:463), [engine.py:5861](engine.py:5861), [dag.py:425](dag.py:425)

**Trigger/configuration:** Default frontier/sweep processing after a session exceeds 100,000 nodes.

**Consequence:** Omitted parents can make already-condensed children appear uncondensed, while genuine frontier nodes disappear from selection. There is no incomplete-graph marker. This confirms the earlier residual; increasing the constant would only move it.

**Checked and qualified:** `source_message_ids` itself uses duplicate-eliminating `UNION`, unlike the cycle-unsafe source-filter query. Ordinary batched deletion has rollback around each batch. `get_source_nodes` reorders children by creation time, but the original ordered `source_ids` remains stored and expansion reads that array directly; I do not count this presentation ordering as independent provenance loss. [dag.py:792](dag.py:792), [dag.py:337](dag.py:337), [tools.py:1389](tools.py:1389)

The unbatched-ID issue is **ST5**.

### db_bootstrap.py

Responsible for connection configuration, schema versioning and migrations, optional schema families, FTS creation, verification, repair and background integrity checks.

**DB1 — A malformed schema-version marker disables the newer-schema guard.**

Both version readers convert malformed values to zero; the refusal hook accepts versions at or below the current version. [db_bootstrap.py:205](db_bootstrap.py:205), [db_bootstrap.py:220](db_bootstrap.py:220), [db_bootstrap.py:238](db_bootstrap.py:238)

**Trigger/configuration:** Default startup with a present but invalid version marker.

**Consequence:** An unknown database is treated as an old database eligible for migrations, without classification or refusal. P34 used `future-v99`; the reader returned zero and the guard did not reject it. This proves the guard failure, not actual raw-row deletion.

**DB2 — Unknown feature schemas can be classified as disposable interim schemas.**

Embedding verification reports unexpected shape as `malformed table`; the newer-shape classifier does not treat that finding as newer for embeddings. The verifier also returns early on missing objects, potentially hiding other incompatible objects. Remediation then selects the entire feature family for deletion. [db_bootstrap.py:408](db_bootstrap.py:408), [db_bootstrap.py:493](db_bootstrap.py:493), [db_bootstrap.py:1491](db_bootstrap.py:1491), [db_bootstrap.py:527](db_bootstrap.py:527)

**Trigger/configuration:** A database stamped newer than this build, containing an unfamiliar shape within an allowlisted family, followed by explicit schema-stamp repair apply. Not automatic default startup deletion.

**Consequence:** The system can misidentify future data as disposable cache data. P15 added `future_payload` to `lcm_embedding_profile`, stamped version 99, and obtained `interim_stamp` plus a plan deleting all four embedding tables.

The command does create a backup before applying. That supplies a recovery route but does not make the classification or “derived caches” assertion correct. [command.py:1130](command.py:1130), [command.py:1171](command.py:1171)

**DB3 — Destructive schema-stamp remediation is not transactional.**

The DROP loop runs without first acquiring an explicit transaction; the version marker is changed afterward. [db_bootstrap.py:611](db_bootstrap.py:611)

**Trigger/configuration:** Explicit repair apply; a failure or competing change during remediation.

**Consequence:** Partial schema destruction survives rollback while the old stamp remains. P16 denied the second table drop: the first table stayed deleted after rollback, and the version remained 99. The command’s backup limits recovery damage, but automatic retry does not restore atomicity.

**DB4 — An unchecked FTS index can be reported healthy and lose its recorded failure.**

`_fts_needs_rebuild` returns false when a deep check is throttled or merely dispatched. The caller treats that result as sufficient to clear `fts_integrity_failed` and return a non-degraded result. Non-finite persisted check timestamps also suppress future checks. [db_bootstrap.py:2791](db_bootstrap.py:2791), [db_bootstrap.py:3011](db_bootstrap.py:3011), [db_bootstrap.py:2473](db_bootstrap.py:2473)

**Trigger/configuration:** Default throttled/background startup with same-row-count index drift; alternatively a malformed `nan`/infinite check timestamp.

**Consequence:** Known search failure becomes invisible to diagnostics while searches still miss content. P13 preserved the row count, changed indexed text, set a failure marker and a recent check timestamp: startup repair cleared the failure and searches still returned empty. P35 confirmed that `nan` makes a check not due.

**DB5 — FTS verification trusts trigger names rather than their definitions.**

Required triggers are checked by name. Repair uses `CREATE TRIGGER IF NOT EXISTS`, so a wrong trigger with the right name survives even an index rebuild. [db_bootstrap.py:2926](db_bootstrap.py:2926), [db_bootstrap.py:3073](db_bootstrap.py:3073), [store.py:293](store.py:293)

**Trigger/configuration:** Default startup/repair with a stale, damaged or incompatible same-name trigger.

**Consequence:** Repair can fix existing index entries while subsequent writes silently stop being indexed. P14 replaced `msg_fts_insert` with a no-op trigger; repair retained it, and a newly inserted message remained unsearchable.

**DB6 — Missing FTS5 prevents startup despite the existence of LIKE fallback.**

Bootstrap unconditionally creates the FTS5 virtual table and does not convert an unavailable module into a supported degraded state. [db_bootstrap.py:3055](db_bootstrap.py:3055)

**Trigger/configuration:** Python linked to SQLite without FTS5. The audit interpreter has FTS5, so this does not describe its deployed runtime.

**Consequence:** Storage initialization fails instead of preserving ingestion and exposing degraded search. P39 injected SQLite’s `no such module: fts5` response and confirmed propagation. A explicitly gates FTS migration and search on availability. [migration.ts:1636](lossless-claw v1.0.0 src/db/migration.ts:1636), [summary-store.ts:1168](lossless-claw v1.0.0 src/store/summary-store.ts:1168)

**DB7 — Background integrity checking still occupies SQLite’s writer boundary.**

The background worker runs FTS integrity checking against the live database. The check is issued as an INSERT inside a savepoint and rolled back only after completion. A separate connection moves execution off the foreground thread; it does not provide a separate SQLite writer. [db_bootstrap.py:2656](db_bootstrap.py:2656), [db_bootstrap.py:2855](db_bootstrap.py:2855)

**Trigger/configuration:** Default background integrity scanning on a large archive, overlapping ingestion or session end.

**Consequence:** A long scan can block writes beyond foreground timeout budgets. The session-end caller explicitly skips final ingestion on a short-wait SQLite lock failure. [engine.py:3511](engine.py:3511)

This is a code-level locking finding; I did not obtain a usable timing result from the attempted shared-memory contention experiment.

**DB8 — The cross-process background-scan claim still races.**

The existing claim is read before `BEGIN IMMEDIATE`. After acquiring that transaction, the claimant writes its timestamp without rechecking whether another process claimed the scan meanwhile. Claim errors are swallowed and scanning still starts. [db_bootstrap.py:2742](db_bootstrap.py:2742)

**Trigger/configuration:** Default background scans, simultaneous startup in separate processes.

**Consequence:** Multiple full integrity scans can be launched despite the claimed single-scan protection, increasing writer contention and producing competing status updates. The process-local lock does not serialize other processes.

**DB9 — Integrity-error details are truncated without a retained full-detail reference.**

Failure metadata stores `str(detail)[:2000]`, with no omitted length or recovery pointer. [db_bootstrap.py:2561](db_bootstrap.py:2561)

**Trigger/configuration:** Any integrity error longer than 2,000 characters.

**Consequence:** This violates the literal no-unmarked-truncation rule for diagnostic content. It is lower impact than transcript loss. P36 confirmed a 2,001-character detail became 2,000 characters with only `at` and `detail` fields. A background warning may contain the full text, but the stored diagnostic does not identify such a recovery location. [db_bootstrap.py:2691](db_bootstrap.py:2691)

**Checked and found sound:** B requests WAL with `synchronous=FULL`; its journal-size setting does not delete raw history. This is stronger committed-write durability than A’s configured `NORMAL`, which should not be copied under this doctrine. [db_bootstrap.py:130](db_bootstrap.py:130), [connection.ts:50](lossless-claw v1.0.0 src/db/connection.ts:50)

The explicit FTS repair ownership context has rollback protection, and non-corruption integrity errors are represented as `unchecked` inside the checker. **DB4 is the caller losing that distinction.** [db_bootstrap.py:2841](db_bootstrap.py:2841), [db_bootstrap.py:2948](db_bootstrap.py:2948)

### sqlite_util.py

Responsible for SQLite-file permission handling, lock-error recognition, savepoints and temporary busy-timeout changes.

**SQ1 — Busy-timeout restoration is incomplete when setup or restoration fails.**

Connection timeouts are changed before entering the `try/finally`. If a later connection fails during setup, earlier changes are never restored. During restoration, one failure also stops restoration of the remaining connections. [sqlite_util.py:222](sqlite_util.py:222)

**Trigger/configuration:** Default session-end timeout wrapper with a closed/failing connection, or a connection closed during scope teardown. [engine.py:3511](engine.py:3511)

**Consequence:** A surviving connection retains the short timeout, causing subsequent ingestion to fail earlier than configured. P03 supplied a live connection followed by a closed one; the live connection remained at 5 ms instead of its original 30,000 ms.

**Checked and found sound:** Savepoint rollback preserves the caller’s outer transaction; P04 retained the outer insert and removed only the failed inner insert. File preparation uses exclusive creation rather than truncation, checks file identity and rejects unsafe file types/links. These paths do not cut database content. [sqlite_util.py:202](sqlite_util.py:202), [sqlite_util.py:32](sqlite_util.py:32), [sqlite_util.py:66](sqlite_util.py:66)

### lifecycle_state.py

Responsible for conversation/session bindings, compacted frontiers, finalization, rollover, maintenance debt and pruning empty lifecycle records.

**LC1 — Per-instance locking does not protect lifecycle read-modify-write operations across connections.**

Bindings and finalization read a snapshot and subsequently overwrite multiple columns without a SQLite transaction covering the read or a conditional update proving the binding is unchanged. `_synchronized` protects only that instance. [lifecycle_state.py:24](lifecycle_state.py:24), [lifecycle_state.py:156](lifecycle_state.py:156), [lifecycle_state.py:263](lifecycle_state.py:263), [lifecycle_state.py:309](lifecycle_state.py:309)

**Trigger/configuration:** Default operation with multiple store instances/processes touching the same conversation.

**Consequence:** Stale finalization can erase a newer session binding and frontier. P24 interleaved two real store instances: the newer session at frontier 30 became `current_session_id=None`, frontier zero.

**LC2 — Finalized frontiers are maximized across different sessions.**

`finalize_session` and `record_rollover` take the maximum of the supplied frontier and the previous finalized frontier without requiring the finalized session IDs to match. [lifecycle_state.py:279](lifecycle_state.py:279), [lifecycle_state.py:327](lifecycle_state.py:327)

**Trigger/configuration:** Default operation when older sessions are resumed or session finalizations arrive out of order.

**Consequence:** A session can be assigned another session’s higher frontier. P25 finalized an older session at 100 after a different session at 900; the stored result named the older session with frontier 900. The boundary handler consumes that value in its own maximum and transfers it onward. [engine.py:2497](engine.py:2497), [engine.py:2607](engine.py:2607)

**LC3 — Rebinding a finalized session forgets its known frontier.**

`bind_session` initializes the current frontier to zero and only preserves a frontier for an already-current matching session. It does not restore the last-finalized frontier when rebinding that same finalized session. [lifecycle_state.py:163](lifecycle_state.py:163)

**Trigger/configuration:** Default session end followed by resumption of the same session identity.

**Consequence:** The engine reloads frontier zero, allowing previously compacted raw history to be treated as uncompacted and summarized again. P26 finalized at 42 and rebound the same session: current frontier zero, last-finalized frontier 42. [engine.py:1835](engine.py:1835), [engine.py:3540](engine.py:3540)

This primarily changes coverage and DAG structure; it does not itself delete raw rows.

**LC4 — Some lifecycle mutators bypass the ownership discipline used by pruning.**

`clear_debt` and `delete_safe_rows_for_sessions` lack the synchronization used elsewhere. The latter selects candidate rows and later deletes by conversation ID without rechecking their current references. Both can commit on the shared connection. [lifecycle_state.py:630](lifecycle_state.py:630), [lifecycle_state.py:812](lifecycle_state.py:812)

**Trigger/configuration:** Concurrent calls on one lifecycle instance; for the deletion helper, concurrent rebinding after its selection. I found no production caller of that deletion helper. Debt operations and automatic empty-row pruning are enabled code paths.

**Consequence:** A mutator can end pruning’s transaction early; the “safe” deletion helper can remove a now-protected/new binding using a stale snapshot.

**Checked and found sound:** `advance_frontier` uses a session-guarded SQL `MAX`, so a lower update or another session cannot regress it; P27 confirmed both cases. Empty-session pruning itself checks both referenced sessions, protects active IDs, and rechecks message/node existence under `BEGIN IMMEDIATE`. Its concern is the unsynchronized neighboring APIs, not a missing data check in its own loop. [lifecycle_state.py:848](lifecycle_state.py:848), [lifecycle_state.py:694](lifecycle_state.py:694)

### reconcile.py

Responsible for recognizing replayed host messages, reconciling an ingest cursor and mapping active message objects to durable source IDs.

**RC1 — Content agreement is treated as proof of occurrence identity.**

Replay identity omits timestamps and stable occurrence identity. Full-replay and stale-prefix rules can consequently classify newly occurring equal-content messages as already stored. [reconcile.py:127](reconcile.py:127), [reconcile.py:685](reconcile.py:685), [reconcile.py:777](reconcile.py:777)

**Trigger/configuration:** Default existing-session reconciliation after restart/rebind, when a new exchange repeats an older exchange or matching prefix.

**Consequence:** New occurrences never reach storage. P17 stored `user: ping`, `assistant: pong`, then supplied the same pair with newer timestamps; reconciliation advanced the cursor past both.

A has explicit transcript-entry IDs and epoch routing available for stronger occurrence evidence. Its fallback identity is still content based, so A is not a blanket proof that this problem is solved in every mode. [reconcile-plan.ts:27](lossless-claw v1.0.0 src/reconcile-plan.ts:27), [reconcile-plan.ts:58](lossless-claw v1.0.0 src/reconcile-plan.ts:58), [message-identity.ts:4](lossless-claw v1.0.0 src/store/message-identity.ts:4)

**RC2 — Source mapping ignores explicit store IDs and silently accepts incomplete mappings.**

The mapper scans candidates by content identity, does not preferentially validate/use a supplied `store_id`, and leaves unmatched messages absent from its returned map. The caller simply omits absent IDs; compaction still removes the selected active span and publishes its node. [reconcile.py:955](reconcile.py:955), [reconcile.py:1161](reconcile.py:1161), [engine.py:4981](engine.py:4981), [compaction.py:991](compaction.py:991)

**Trigger/configuration:** Default compaction with repeated content, reordered/subset active history, or an identity mismatch.

**Consequence:** A summary can cite the wrong occurrence or lack provenance for part of what it summarizes. P18 supplied the actual stored row with ID 3; the mapper returned ID 1. This also makes DG2’s empty-source publication reachable through the engine.

**RC3 — Tool-call canonicalization changes the meaning of literal string arguments.**

Canonicalization recursively parses every JSON-looking string, including string values nested inside tool arguments, then sorts and rewrites it. [reconcile.py:57](reconcile.py:57)

**Trigger/configuration:** Default reconciliation/source mapping for calls containing JSON-looking literal strings and otherwise matching call identity.

**Consequence:** Distinct tool inputs can acquire the same replay identity and be skipped or mapped incorrectly. P05 used two different literal `text` values containing differently formatted/ordered JSON; their identities collided. Normalizing the serialized argument object is different from normalizing strings *inside* that object.

**RC4 — Any embedded externalized reference can replace the identity of the whole message.**

After finding a reference anywhere in content, reconciliation loads the payload and replaces the entire content identity with `payload["content"]`. It does not require the whole message to be that placeholder or verify its ownership at this point. [reconcile.py:228](reconcile.py:228), [externalize.py:926](externalize.py:926)

**Trigger/configuration:** A message quoting a valid retained externalized reference. This branch is not guarded by the current externalization-enabled flag; previously created payloads suffice.

**Consequence:** Text before and after the reference disappears from equality checks, enabling false replay or incorrect source mapping. P19 supplied “Before [reference] AFTER new fact”; identity became only the payload content, even with a fixture payload belonging to another session.

**RC5 — Durable persisted-output replay wildcarding does not prove equality to the stored generation.**

The helper proves that the candidate has a durable payload and that the stored row represents a persisted output, then replaces both contents with the same wildcard. It compares role/call identity rather than proving they reference the same payload generation. [reconcile.py:285](reconcile.py:285), [reconcile.py:291](reconcile.py:291)

**Trigger/configuration:** Persisted tool outputs with durable externalization, reused call identity, and different archived generations—for example after a partial previous ingest. Externalization is opt-in in the documented configuration.

**Consequence:** A new output can be treated as already persisted because an older generation occupies the replay position. P40 supplied different candidate/stored payload identities with the two independent durability predicates satisfied; the real comparison returned true. Those predicates were stubbed in this comparison probe; it was not a filesystem recovery test.

**RC6 — Empty-session reconciliation accepts a digest suffix as a generated-placeholder credential.**

The empty-session path extracts any terminal `sha256=<16 hex>]` and consults counts/ordinals. It does not require the full generated-placeholder envelope or role. [reconcile.py:814](reconcile.py:814), [placeholder_ledger.py:49](placeholder_ledger.py:49)

**Trigger/configuration:** An empty session with retained generated-placeholder counts/ordinals, normally from ignore handling.

**Consequence:** Ordinary new text ending in a known digest can be skipped without storage. P20 used `Keep this new fact sha256=…]`; reconciliation advanced the cursor over it.

**RC7 — Reconciliation repeatedly rescans every candidate prefix.**

For each cursor position, the function slices and filters the prefix, rebuilds identities and evaluates replay evidence. These are repeated whole-prefix operations. [reconcile.py:449](reconcile.py:449)

**Trigger/configuration:** Default reconciliation of a large unmatched/ambiguous message array, especially a 1M-token context containing many short messages.

**Consequence:** Quadratic work delays ingestion and makes time-budget failures more likely. P23’s isolated unmatched fixtures took approximately 31, 91 and 334 ms for 100, 200 and 400 messages. These are fixture timings, not a production benchmark; the nested prefix work is visible in the code.

**Checked and found sound:** Candidate loading for source mapping is genuinely paginated to exhaustion. Ambiguous ordinary singleton deltas are not automatically dropped by the stale-prefix rule. These safeguards do not establish occurrence identity for the multi-message cases above. [reconcile.py:966](reconcile.py:966), [reconcile.py:792](reconcile.py:792)

### placeholder_ledger.py

Responsible for identifying generated ignore placeholders, persisting their hashes/counts/ordinals, carrying dependent-reply decisions across sessions and rewriting ignored active messages.

**PL1 — Ignored-message placeholders contain no recoverable source.**

The placeholder records size and a shortened digest, but no durable content reference. Rewriting an ignored assistant message also removes its tool-call fields. The ingest caller deliberately skips storing the original. [placeholder_ledger.py:54](placeholder_ledger.py:54), [placeholder_ledger.py:665](placeholder_ledger.py:665), [engine.py:4873](engine.py:4873)

**Trigger/configuration:** Nonempty ignore patterns matching a message. Disabled by the documented default.

**Consequence:** Explicitly marked loss remains loss: a digest cannot recover the source or explain its substance. The configuration is incompatible with the operator’s absolute doctrine, despite being intentional behavior.

**PL2 — Durable correctness records are silently evicted at 512 entries.**

Generated-placeholder hashes and dependent-reply records are sliced to their last 512 entries on write; dependent records are also sliced on read. [placeholder_ledger.py:192](placeholder_ledger.py:192), [placeholder_ledger.py:448](placeholder_ledger.py:448), [placeholder_ledger.py:486](placeholder_ledger.py:486)

**Trigger/configuration:** Ignore/dependent-reply handling over a sufficiently long session.

**Consequence:** Restart/rollover loses the evidence needed to distinguish generated placeholders and dependent occurrences from literal messages. No eviction marker or recovery route exists. P21 confirmed silent removal of the oldest hash when entry 513 was added. This should be durable state, not a window-scaled cache.

**PL3 — Ledger read/write failures masquerade as empty/successful state, and updates can overwrite each other.**

Read failures return empty collections. Read-modify-write operations then replace whole metadata values. Write failures are logged at debug level and swallowed, while in-memory state can still be updated. There is no transaction spanning the read and replacement across instances. [placeholder_ledger.py:173](placeholder_ledger.py:173), [placeholder_ledger.py:192](placeholder_ledger.py:192), [placeholder_ledger.py:411](placeholder_ledger.py:411), [placeholder_ledger.py:512](placeholder_ledger.py:512)

**Trigger/configuration:** Ignore/dependent ledgers in use, plus a transient read/write failure or concurrent updates.

**Consequence:** Decisions presented as durable can disappear on restart; a failed read can destroy previously valid ledger contents on the next successful write. P22 injected a read error into a populated ledger; remembering one new hash replaced the entire ledger with that hash.

**PL4 — Rollover copies dependent-reply state from only the first message page.**

The copy helper calls `get_session_messages_after` once with its default 10,000-row limit. It excludes dependent records whose store fingerprints are absent from that partial scan. Scan exceptions produce the same effective omission. [placeholder_ledger.py:142](placeholder_ledger.py:142), [store.py:859](store.py:859)

**Trigger/configuration:** Compression rollover with dependent-reply records and more than 10,000 source rows after the frontier. The engine calls it with `copy_dependent_content=True`. [engine.py:2548](engine.py:2548)

**Consequence:** Later dependent-reply decisions disappear from the carried ledger without a marker. P32 placed the relevant record at row 10,001: one source record existed and zero target records were copied.

**PL5 — Rollover removes occurrence identity from dependent-reply records.**

Carried records become content-only pending records. A later matching assistant/tool message can consume such a record and become marked dependent even when it is a new independent occurrence. [placeholder_ledger.py:160](placeholder_ledger.py:160), [placeholder_ledger.py:527](placeholder_ledger.py:527), [placeholder_ledger.py:551](placeholder_ledger.py:551)

**Trigger/configuration:** Ignore-dependent rollover state followed by repeated response content; particularly when the original pending occurrence is absent from the new replay.

**Consequence:** Independent content can be excluded from summarization/provenance as an old dependent reply. P33 supplied a new `Done` occurrence with a different store ID and timestamp; it matched a content-only pending record.

**Checked and found sound:** Stored-placeholder counting pages through the entire session. I initially suspected rollover omitted counts/ordinals entirely; the engine copies those separately, so that suspicion was incorrect. The remaining rollover defects are the incomplete dependent-row scan and loss of occurrence binding. [placeholder_ledger.py:372](placeholder_ledger.py:372), [engine.py:2554](engine.py:2554)

The digest-extraction helper’s unsafe use as authentication is **RC6**.

## D. Cross-partition notes

1. **Compaction must reject incomplete provenance before consuming the active span.** Fixing the mapper alone is insufficient: the caller currently publishes whatever IDs it receives and advances to the maximum consumed ID. The compaction partition should enforce complete substantive-source coverage and a contiguous, justified frontier transition. [compaction.py:991](compaction.py:991)

2. **GC’s archive callback swallows the very failure its transaction is intended to prevent.** `_archive_chunks_for_messages` catches ordinary exceptions even when operating on the GC transaction’s connection. Thus fixing ST3’s rollback handling alone will not make chunk archival atomic. [engine.py:3656](engine.py:3656), [engine.py:5167](engine.py:5167)

3. **GC can select a sanitized payload before the exact original.** Its candidate order prefers `sanitize_pre_compaction_content(content)` when different. The externalization/ingest-protection partition should require proof that the retained payload reconstructs the exact stored source before allowing rewrite. This remains opt-in GC behavior. [engine.py:5205](engine.py:5205)

4. **Carried DAG nodes still encounter current-session-only child expansion.** Reassignment preserves references to old-session children, but the expansion loop skips those children. Recovery authorization needs to follow verified lineage rather than require every child to share the current session. [engine.py:2573](engine.py:2573), [tools.py:1389](tools.py:1389)

5. **Rotate still advances its durable frontier before writing the explanatory node.** A marker-write failure can therefore leave skipped history without the intended index entry. This needs the publication transaction from DG3, with a test specifically covering rotate. [engine.py:6841](engine.py:6841), [engine.py:6874](engine.py:6874), [engine.py:6920](engine.py:6920)

6. **Node metadata has an independent cut and an overbroad exception handler.** `extract_index_block` truncates with an ellipsis but no exact recovery instruction; the full summary still exists, so this is recoverable-source presentation loss rather than raw deletion. `delete_many` treats every `OperationalError` as an absent table, potentially concealing failed sidecar cleanup. [node_meta.py:61](node_meta.py:61), [node_meta.py:120](node_meta.py:120)

7. **Maintenance flushes need a shared ownership review.** Besides ST4, maintenance commits DAG and lifecycle connections directly. Those calls can interfere with transactions owned by their respective stores. [maintenance.py:63](maintenance.py:63)

8. **The optional redaction contract remains incompatible with absolute no-loss operation.** The README explicitly says matched values become unrecoverable before storage. This belongs to ingest protection, but configuration validation should prevent accidentally enabling it in the doctrine-compliant deployment. [README.md:517](README.md:517)

9. **The claimed downgrade barrier needs verification beyond the sidecar classifier.** The design discusses a newer-schema classification for `lcm_node_meta`, but the startup guard examined here invokes classification only when the numeric version is already too high. Sidecar presence alone is not a refusal check in this code. [docs/fork-design.md:447](docs/fork-design.md:447), [db_bootstrap.py:238](db_bootstrap.py:238)

10. **Do not promote every earlier comparison candidate into a storage defect.** `describe_subtree` intentionally returns metadata; omission of its own summary is an interface limitation, not by itself proof of lost provenance. Its omission of *missing-child errors* is the concrete defect already counted in DG2. Likewise, A’s relational lineage and occurrence IDs are useful patterns, while its weaker durability setting and bounded reconciliation policies should not be imported wholesale. [dag.py:877](dag.py:877), [connection.ts:57](lossless-claw v1.0.0 src/db/connection.ts:57), [reconcile-plan.ts:13](lossless-claw v1.0.0 src/reconcile-plan.ts:13)
