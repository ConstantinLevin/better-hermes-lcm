**The main architectural change should be one publication contract shared by foreground compaction, rotation, repair, and eventual background preparation.**

Today, leaf publication commits the node, commits metadata separately, runs follow-up work, changes an in-memory cursor, then advances lifecycle state through another connection. Condensation repeats the node/metadata split. Wrapping the callers in a transaction will not fix independently committing helpers or separate connections. [B compaction.py:1019](compaction.py:1019), [B dag.py:250](dag.py:250), [B node_meta.py:84](node_meta.py:84), [B lifecycle_state.py:68](lifecycle_state.py:68)

I would define:

- An immutable **source snapshot**: ordered source identities and revisions/hashes, session binding/generation, expected frontier, relevant configuration and prompt version.
- A **candidate result**: complete output, termination evidence, source-coverage information, metadata, and measured token counts.
- One short **publication transaction**: revalidate the snapshot; insert node, provenance, and metadata; advance the appropriate frontier; record necessary derived-index invalidations. Update in-memory state only after commit.
- An idempotent retry rule: the same operation either returns its existing publication or rejects a stale snapshot. Slow model calls stay outside the transaction.

This subsumes T1.3, the preventive half missing from T1.5, publication-related parts of T3.3, and the storage foundations of T5.1/T5.2. It does **not** subsume semantic quality or retrieval authorization.

A supplies useful examples: transactional node/edge/context replacement, source-fingerprint checks, and worker-claim matching. But its transaction mutex is keyed by an in-process database handle; copying it is not a cross-process solution. [A compaction.ts:2324](lossless-claw v1.0.0 src/compaction.ts:2324), [A pending-summary-coordinator.ts:660](lossless-claw v1.0.0 src/pending-summary-coordinator.ts:660), [A pending-summary-store.ts:703](lossless-claw v1.0.0 src/store/pending-summary-store.ts:703), [A transaction-mutex.ts:25](lossless-claw v1.0.0 src/transaction-mutex.ts:25)

The “new module per finding” tendency comes mainly from the earlier port proposals, rather than an explicit module list in `TASKS.md`. Nevertheless, the implementation should reject that tendency. Module count is not mergeability. A small SQL correction is easier to maintain than a new wrapper plus imports plus duplicated query semantics. Conversely, a shared publisher earns its abstraction because it removes several independently incorrect write sequences. The existing touchpoints document already records how many scattered hooks must be reapplied. [touchpoints:6](docs/fork-touchpoints.md:6)

**Several assumptions need to become explicit requirements before implementation.**

**Existing data cannot acquire evidence retroactively.** The current sidecar stores level, index text, and update time; it does not store prompt version, generation termination, source fingerprints, or validation status. Creating new columns cannot honestly label old nodes “complete” or “L1.” Some index text can be reconstructed from the stored summary; missing termination evidence cannot. Old provider cutoffs may have no recognizable marker. [B node_meta.py:46](node_meta.py:46), [B escalation.py:262](escalation.py:262)

Require a migration/backfill specification for provenance enforcement, richer node metadata, payload catalogs, pending work, and revisions. It must cover resumability, concurrent writers, invalid existing edges, source/payload hashes before and after, and explicit `unknown`/`incomplete` states. New tables also need deliberate schema-classifier registration; B does not accept arbitrary feature families. [B db_bootstrap.py:309](db_bootstrap.py:309)

**Historical repair must bypass the behavior that caused degradation.** Repairing from “sources” through today’s serializer can repeat its per-message elisions, externalized-head substitution, and preprocessing removal. Repair needs verified, hydrated originals and a source-complete preparation path. Re-condensing defective child text cannot recover topics already missing from that text. [B engine.py:5230](engine.py:5230), [B extraction.py:232](extraction.py:232), [B engine.py:5807](engine.py:5807)

**SQLite write serialization is not stale-work validation.** Two processes can summarize the same old frontier and then commit sequentially. `MAX(current_frontier_store_id, …)` prevents checkpoint regression; it does not reject the second obsolete node. Likewise, lookahead retains mutable message objects and calls a method bound to the engine, whose serializer reads current configuration and session state. Deadline work must not release ownership and leave late workers using a subsequently rebound engine. [B lifecycle_state.py:863](lifecycle_state.py:863), [B leaf_pipeline.py:94](leaf_pipeline.py:94), [B compaction.py:405](compaction.py:405), [B engine.py:5247](engine.py:5247)

**The 256k constraint needs explicit tests and conflict resolution.** The current low-window path deliberately uses the upstream depth loop; the positive-budget path switches to age ordering. A shared planner must not accidentally erase that distinction. T3.2 can create nodes upstream would not create; T3.5 can change fan-in; speculative preparation can choose source groups too early. These are not automatically “pure improvements” merely because their intentions are good. [B engine.py:5652](engine.py:5652), [B engine.py:5682](engine.py:5682)

Specify the preserved topology contract: source membership, ordering, depths, publication sequence, and frontier under controlled successful responses. Test real multi-turn traces as well: summary lengths feed subsequent pressure calculations, so unchanged configuration values alone do not prove unchanged behavior. The current 1M chunking test uses tiny chunks and a supplied `900_000` token estimate; it proves scheduling mechanics, not operation on a populated 1M context. [B compaction.py:1031](compaction.py:1031), [B test_weighted_chunking.py:55](tests/fork/test_weighted_chunking.py:55)

Where a proposed correction conflicts with literal 256k DAG identity, document the conflict before implementation. Internal source subdivision that ultimately publishes the original canonical group may preserve topology; publishing smaller canonical groups does not. Do not quietly redefine the doctrine.

**Phase 0 should produce one coherent contract with several renderings—not several independent policies.**

The contradictions are real: L1 requires every topic, then allocates 60–70% to focus and permits dropping resolved topics; L2 says both “Maximum” and “Exceed the maximum.” Its `source_depth` changes provenance but does not select depth-specific bullet instructions. [B escalation.py:436](escalation.py:436), [B escalation.py:502](escalation.py:502)

I would structure the design around these distinctions:

- **Shared invariants:** every source topic remains discoverable; assertions stay attributed; rejected approaches retain their reasons; uncertainty and supersession remain explicit; provenance and omissions survive.
- **Leaf operation:** identify events/topics from original messages, including what tools were asked to do and what their results established.
- **Parent operation:** merge child indexes while preserving a route to every child’s subjects. Increasing depth changes organization and wording, not permission to erase process-related topics.
- **L1/L2 presentation:** prose versus compact bullets, with the same coverage obligations. L2 cannot mean “weaken the index until it fits.”
- **Task focus:** optional emphasis after coverage, preferably transient presentation rather than a durable omission rule. A has a separate focus-brief representation; that separation is useful, but B does not need the whole feature to remove focus-driven omission. [A assembler.ts:1204](lossless-claw v1.0.0 src/assembler.ts:1204)
- **Other callers:** explicitly inventory rollups and repair. B’s rollup builder repeatedly feeds summaries back through escalation until a hard cap is met. A leaf/deep-depth document alone will miss that mode. [B rollup_builder.py:257](rollup_builder.py:257)

A worthwhile prompt design document must contain more than polished instructions:

1. **Annotated source-to-index examples**, including hard negatives: identical identifiers but opposite decisions; a completed task whose method matters; an off-focus rejected option; a late tool error.
2. **An input contract:** ordered source handles, child boundaries, trustworthy timestamps, unknown timestamps, hydrated payloads, and explicit source omissions.
3. **An output contract:** how a reader identifies subjects and recovery handles; how completion and coverage are checked; the behavior for malformed, ambiguous, empty, incomplete, and non-shrinking output.
4. **Instruction precedence:** coverage before style/focus/length; custom instructions remain bounded preferences. Keep source and request values inside the existing untrusted-data envelope, not interpolated into trusted instructions. [B prompt_boundary.py:18](prompt_boundary.py:18)
5. **Budget accounting:** advisory target, actual serialized request, output allowance, route capacity, retries, and one deadline. The main model’s window and the operator’s summarizer capacity are separate quantities.
6. **Compatibility/versioning:** footer extraction, sidecar representation, historical nodes, rendered headers, scaffold recognition, and repair invalidation.
7. **A predeclared experiment and release decision**, including failure thresholds and cases that must never regress.

There are several ways the new prompt could break the system besides hitting a generation limit:

- Longer indexes can fail the strict “shorter than source” acceptance check, or alter future pressure and condensation timing. [B escalation.py:582](escalation.py:582)
- More verbose child indexes increase deep-parent input and output demand. [B engine.py:5807](engine.py:5807)
- A changed footer can break extraction; the current extractor searches for one exact marker and retains only 1,600 characters. [B node_meta.py:61](node_meta.py:61)
- Repeated full coverage lists can consume the prompt with duplicate indexing, making navigation worse despite more retained words.
- Removing historical-state distinctions can cause completed work to look actionable again; preserving those distinctions does not require calling everything outside the current focus stale.
- New wrappers and metadata can change assembly selection and replay recognition. [B engine.py:6323](engine.py:6323)

Measure the production path: **real summarization → actual assembled prefix → independent reader using actual recovery tools → exact source recovery**. Keep test questions and expected handles out of summarizer input. Report topic discoverability, valid navigation paths, retrieved source identity, exact reconstruction, wrong-state/unsupported answers, calls, tokens, latency, retries, and failure rate. Stratify by depth, L1/L2, topic position, focus switches, payload externalization, session rollover, and genuinely populated low/intermediate/1M contexts.

Use source-annotated obligations, not just keyword matching. Include a deliberately bad “bag of identifiers” summary and require the evaluator to reject it. Measure both child-to-parent preservation and root-to-original-source discoverability; checking parents only against already-degraded children hides accumulated loss. That is what the current doctor does for node-sourced nodes. [B coverage_doctor.py:96](coverage_doctor.py:96)

No finite real-model evaluation proves universal semantic losslessness. It can reject known failures and quantify residual uncertainty. The plan should say that plainly rather than turn a percentage into certification.
